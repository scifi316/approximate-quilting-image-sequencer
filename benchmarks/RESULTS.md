# Faiss index type benchmark results

Generated by `benchmarks/faiss_index_benchmark.py`. Measures the pipeline's
actual usage pattern: build the index once per dataset change, then run many
batched `top_k` searches per target frame (the access pattern of
`stitch.matchFeaturesBatch`).

## Real dataset (683,312 SIFT descriptors, 5,112 frames, dim=128)

```
python benchmarks/faiss_index_benchmark.py --dataset real --repeats 2 --json benchmarks/real_dataset_results.json
```

| index_type    | build_s | size_MB | query_ms  | recall@7 |
|---------------|--------:|--------:|----------:|---------:|
| flat          |    0.04 |   349.9 | 67,422.07 |  100.00% |
| ivfflat       |  446.05 |   357.0 |     92.21 |   99.23% |
| hnsw          |    8.72 |   535.8 |     12.55 |   98.85% |
| ivfpq         |  428.76 |    18.2 |     53.33 |   77.54% |
| flat+gpu      |    0.07 |   349.9 |     76.64 |   99.83% |
| ivfflat+gpu   |    1.71 |   357.0 |     11.95 |   99.09% |

(`query_ms` is the average latency of one batched `search()` call over a
2,000-descriptor query batch, mirroring one target frame's chunk
descriptors handed to `matchFeaturesBatch`.)

## Takeaways

- **The current baseline (`IndexFlatL2`, exact brute force) is the
  bottleneck.** One batched query took ~67 seconds on this dataset. At
  hundreds of chunks per target frame's `matchFeaturesBatch` call, this
  alone explains the "2-3 FPS" complaint in `docs/INSTALL.md`.
- **`hnsw` is the best CPU-only, no-training default.** ~5,370x faster
  queries than flat, no training step (so it keeps the incremental
  per-frame `add()` that avoids holding the whole dataset in memory), no
  GPU dependency, and only a modest recall drop (98.85% vs. exact). Its
  only downside is a larger on-disk footprint (~536MB vs. ~350MB for flat
  on this dataset) since it stores a navigable graph alongside the raw
  vectors.
- **`ivfflat` matches `hnsw`'s recall and beats it on size**, but building
  it took ~7.5 minutes on CPU (k-means training on the coarse quantizer is
  the expensive part) vs. ~9 seconds for `hnsw`. That's a one-time cost per
  dataset change, so it's a reasonable choice if the larger `hnsw` index
  size is the constraint and a several-minute rebuild is acceptable.
- **`ivfpq` has real value (18MB, a 19x size reduction) but recall drops to
  77.5%** at this dataset's scale -- for a voting-based nearest-neighbor
  match like `matchFeaturesBatch`, that's a meaningfully worse candidate
  pool per chunk. Only worth it if index size becomes the binding
  constraint (e.g. a dataset too large to fit in memory).
- **GPU changes the calculus entirely for IVF training**: `ivfflat+gpu`
  builds in ~1.7 seconds (vs. ~446s on CPU) and matches `hnsw` on query
  latency, because k-means training runs on the GPU instead of walking the
  683K-point training sample on CPU each iteration. `requirements.yml`
  already provisions CUDA + `faiss-gpu`, so this is effectively free for
  anyone running the documented conda environment on a CUDA machine.
  `build_database.py` wires this up as an opt-in (`use_gpu=True` /
  `FAISS_USE_GPU=1`), not the default, since `requirements.txt` (the
  pip-only path) only provides `faiss-cpu` and the default build path
  should work without a GPU. The GPU is only used during training/add; the
  result is converted back to a plain CPU index before being written, so no
  GPU is needed later to load or query it.

## Default: `hnsw`

`build_database.py`'s `DEFAULT_INDEX_TYPE` is `"hnsw"`: it needs no CUDA
dependency, no training step (so the low-memory incremental per-frame
`add()` from the earlier bugfix pass still applies), and delivers the
second-best query latency in this benchmark for a middling size cost.
Override it per-run with the `FAISS_INDEX_TYPE` environment variable, e.g.:

```
FAISS_INDEX_TYPE=ivfflat python src/database/build_database.py
```

## Synthetic dataset (fast iteration)

```
python benchmarks/faiss_index_benchmark.py --dataset synthetic --synthetic-size 20000
```

Useful for quickly sanity-checking a change to the benchmark harness itself
without waiting on the real dataset's multi-minute IVF/PQ training; results
at this small scale (see the `recall@7` gap on `ivfpq` above, which needs a
much larger training set to be meaningful) are not representative and
shouldn't be used to pick a default.

## Notes on running this yourself

- Requires `individual_descriptors_faiss_index.bin` at the repo root
  (`--dataset real` reconstructs the raw descriptors from it) -- run
  `python src/database/build_database.py` first if it doesn't exist.
- Faiss's IVF/PQ training re-scans the full training set on every k-means
  iteration (25 by default); the harness caps the training sample at
  `TRAIN_SAMPLE_CAP` (200K vectors) and still `add()`s every descriptor
  afterward -- training on a representative subsample is standard Faiss
  practice and produces effectively the same centroids at a fraction of the
  cost.
- If Faiss's OpenMP thread pool isn't picking up all available cores in
  your environment (symptom: CPU time roughly equal to wall-clock time
  despite many threads existing, i.e. no real parallelism), pass
  `--threads N` explicitly; the harness calls `faiss.omp_set_num_threads()`
  itself rather than relying on the environment's default.
